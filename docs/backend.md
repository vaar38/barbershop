# Бэкенд Fade

REST API сервиса записи в барбершопы. Python 3.14, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 18.

Общее описание проекта, ER-диаграмма и бизнес-правила — в [readme](../readme.md). Почему выбраны именно эти технологии — в [stack.md](stack.md).

Интерактивная документация всех эндпоинтов (Swagger) открывается после запуска: `http://localhost/docs`.


## 1. Структура

```
backend/
├── Dockerfile               образ: миграции + uvicorn
├── requirements.txt         зависимости (версии зафиксированы)
├── alembic.ini
├── alembic/
│   ├── env.py               берёт адрес базы из config.py и модели из models.py
│   └── versions/
│       └── 4f55d048efea_create_tables.py   таблицы, EXCLUDE-ограничение, роли
└── app/
    ├── main.py              создаёт приложение и подключает роутеры
    ├── config.py            настройки из переменных окружения
    ├── database.py          подключение к базе и сессия на запрос
    ├── models.py            11 таблиц (SQLAlchemy)
    ├── schemas.py           что API принимает и отдаёт (Pydantic)
    ├── security.py          пароли, JWT, текущий пользователь, проверка роли
    ├── seed.py              демо-данные
    └── routers/             эндпоинты по разделам
        ├── auth.py          регистрация, вход, обновление токенов, выход
        ├── users.py         свой профиль
        ├── branches.py      филиалы
        ├── categories.py    категории услуг
        ├── services.py      услуги
        ├── masters.py       мастера, отзывы, свободное время, смены
        ├── shifts.py        удаление смены
        ├── appointments.py  записи, статусы, отмена, отзыв
        └── stats.py         статистика для администратора
```

Каждый роутер — отдельный раздел API со своим префиксом (`/api/masters`, `/api/appointments`…). Внутри роутера лежат функции-эндпоинты и мелкие вспомогательные функции, которые нужны только этому разделу.


## 2. Как проходит запрос

```
HTTP-запрос
  → nginx (/api/…)            проксирует на backend:8000
  → FastAPI                   находит эндпоинт по методу и пути
  → Pydantic-схема            проверяет тело и параметры, иначе 422
  → зависимости (Depends)     get_db — сессия базы; get_current_user — пользователь по токену;
                              require_admin — проверка роли
  → функция эндпоинта         бизнес-проверки, запросы через SQLAlchemy, commit
  → response_model            ответ фильтруется по схеме (лишние поля, например password_hash, не уходят)
```

**Сессия базы.** `get_db()` в [database.py](../backend/app/database.py) открывает сессию на время запроса и закрывает её после ответа (`yield` + `finally`). Эндпоинт получает её параметром `db: Session = Depends(get_db)`.

**Транзакции.** Всё, что эндпоинт меняет, сохраняется одним `db.commit()`. Например, запись и её состав (`appointments` + `appointment_services`) попадают в базу вместе или не попадают совсем.


## 3. Настройки

Читаются из переменных окружения (локально — из `backend/.env`, в Docker — из корневого `.env` через `docker-compose.yml`).

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DATABASE_URL` | адрес PostgreSQL для SQLAlchemy | `postgresql+psycopg://postgres:postgres@localhost:5432/fade` |
| `SECRET_KEY` | ключ подписи JWT | dev-значение, в проде обязательно заменить |
| `TIMEZONE` | часовой пояс сети | `Europe/Moscow` |

Время жизни токенов задано в [config.py](../backend/app/config.py): access — 30 минут, refresh — 7 дней.


## 4. База данных

### Таблицы

| Таблица | Что хранит |
|---|---|
| `roles` | роли: client, master, admin (заполняются миграцией) |
| `users` | все пользователи: email, хеш пароля, имя, телефон, роль, `token_version` |
| `branches` | филиалы; `is_active = false` — филиал закрыт |
| `service_categories` | категории услуг |
| `services` | услуги: длительность в минутах, базовая цена, `is_active` |
| `masters` | профиль мастера: пользователь, филиал, уровень (junior / middle / top), `is_active` |
| `master_services` | какие услуги делает мастер (многие-ко-многим) |
| `work_shifts` | смены: мастер, филиал, дата, время начала и конца (местное время) |
| `appointments` | записи: клиент, мастер, филиал, `start_at`, `end_at` (timestamptz), статус, итоговая цена |
| `appointment_services` | состав записи: услуга, цена и длительность на момент записи |
| `reviews` | отзывы: запись (одна), оценка 1–5, текст |

Связи — на ER-диаграмме в [readme](../readme.md#данные).

### Ограничения в базе

Правила, которые нельзя нарушить даже в обход API:

| Ограничение | Что запрещает |
|---|---|
| `ck_services_duration`, `ck_services_price` | услугу с нулевой длительностью или ценой |
| `ck_masters_level` | уровень мастера кроме junior / middle / top |
| `ck_work_shifts_time` | смену, которая кончается раньше начала |
| `ck_appointments_time` | запись с `end_at <= start_at` |
| `ck_appointments_status` | неизвестный статус |
| `ck_appointments_price` | отрицательную цену |
| `ck_reviews_rating` | оценку вне 1–5 |
| `UNIQUE` на `users.email`, `branches.name`, `service_categories.name`, `masters.user_id`, `reviews.appointment_id` | дубли; второй отзыв на ту же запись |
| **`ex_appointments_no_overlap`** | две активные записи одного мастера на пересекающееся время |

Последнее — главное ограничение проекта:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE appointments ADD CONSTRAINT ex_appointments_no_overlap
EXCLUDE USING gist (
    master_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
) WHERE (status IN ('pending', 'confirmed'));
```

Читается так: не может быть двух строк, у которых `master_id` равен, а интервалы времени пересекаются (`&&`). Интервал полуоткрытый `[)`, поэтому записи 12:00–13:15 и 13:15–14:00 не конфликтуют. Отменённые и завершённые записи время не занимают (условие `WHERE`). Расширение `btree_gist` нужно, чтобы в одном индексе GiST сравнивать обычное число (`master_id`) и интервал.

### Миграции

Схема создаётся Alembic-миграцией [4f55d048efea](../backend/alembic/versions/4f55d048efea_create_tables.py). Таблицы сгенерированы из моделей (`alembic revision --autogenerate`), а то, что Alembic не умеет описывать сам — расширение, `EXCLUDE` и начальные роли, — дописано вручную через `op.execute`.

```
alembic upgrade head      применить миграции
alembic downgrade -1      откатить последнюю
```

В Docker миграции применяются автоматически при каждом старте контейнера (`CMD` в [Dockerfile](../backend/Dockerfile)).

### Удаление

Филиалы, услуги и мастера **не удаляются**, а выключаются (`is_active = false`): на них ссылаются старые записи и отзывы, и история должна сохраниться. Выключенные пропадают из каталога и из записи. Категорию удалить можно, только если в ней нет услуг (иначе 409). Смену можно удалить, только если на неё нет активных записей (иначе 409).


## 5. Авторизация и роли

### Пароли

Хранятся только как bcrypt-хеш (`pwdlib`). При входе `verify_password` сравнивает введённый пароль с хешем.

### Токены

После входа клиент получает пару JWT (подпись HS256, ключ `SECRET_KEY`):

| | Срок | Для чего |
|---|---|---|
| access | 30 минут | передаётся в каждом запросе: `Authorization: Bearer <token>` |
| refresh | 7 дней | только для `POST /api/auth/refresh`, чтобы получить новую пару |

Внутри токена:

```json
{ "sub": "12", "ver": 3, "type": "access", "exp": 1767225600 }
```

`get_user_from_token` в [security.py](../backend/app/security.py) проверяет подпись и срок, тип токена (refresh нельзя использовать вместо access), что пользователь существует и что `ver` совпадает с `users.token_version`.

**Выход.** `POST /api/auth/logout` увеличивает `token_version` на 1. После этого все ранее выданные токены пользователя (на всех устройствах) перестают проходить проверку `ver` — хранить чёрный список токенов не нужно.

### Роли

Роль хранится в `users.role_id`. Регистрация через API всегда даёт роль `client`; мастеров создаёт администратор (`POST /api/masters` создаёт пользователя с ролью `master` и его профиль); администратор появляется из демо-данных или вручную в базе.

Права проверяются зависимостями:

| Зависимость | Пускает |
|---|---|
| `get_current_user` | любого вошедшего |
| `require_admin` | только администратора |
| `get_role_name` + проверка в эндпоинте | когда правило зависит от роли (например, клиент видит свои записи, мастер — к себе) |

| Действие | Гость | Клиент | Мастер | Админ |
|---|:-:|:-:|:-:|:-:|
| каталог, мастера, отзывы, свободное время | ✓ | ✓ | ✓ | ✓ |
| профиль | | ✓ | ✓ | ✓ |
| создать запись | | ✓ | | |
| список и карточка записи | | свои | к себе | все |
| отменить запись | | свою, за 2 ч | | любую |
| сменить статус | | | к себе | любую |
| оставить отзыв | | на свою выполненную | | |
| смены мастера | | | свои (просмотр) | все |
| справочники, мастера, статистика | | | | ✓ |

**Чужая запись — 404, а не 403.** Если клиент запросит запись другого клиента по id, сервер отвечает так же, как на несуществующую. Так по ответам нельзя узнать, какие id заняты (функция `find_visible` в [appointments.py](../backend/app/routers/appointments.py)).


## 6. Бизнес-правила в коде

| Правило | Где проверяется |
|---|---|
| конец записи и цену считает сервер, клиент шлёт только `start_at` | схема `AppointmentCreate` не содержит этих полей; расчёт в `create_appointment` |
| цена = база × коэффициент уровня (1.0 / 1.2 / 1.5), считается в `Decimal` | `LEVEL_FACTOR` в `appointments.py` |
| цена и длительность копируются в `appointment_services` | `create_appointment`, шаг 7 |
| запись целиком внутри смены и на сетке 15 минут | `create_appointment`, шаг 4 |
| нельзя записаться в прошлое | `create_appointment`, шаг 3 |
| нет пересечения с активной записью мастера | проверка запросом (шаг 5) **и** `ex_appointments_no_overlap` в базе |
| клиент отменяет не позже чем за 2 часа, админ — всегда | `cancel_appointment`, `CANCEL_DEADLINE` |
| переходы статусов только pending → confirmed → completed / no_show | `NEXT_STATUS` в `change_status` |
| итог визита — только после начала записи | `change_status` |
| отзыв — только своя запись в статусе completed, один на запись | `create_review` + `UNIQUE (reviews.appointment_id)` |
| один часовой пояс сети | `TZ` из `config.py`, смены переводятся в `timestamptz` через `datetime.combine(..., tzinfo=TZ)` |

### Свободное время мастера

`GET /api/masters/{id}/slots?date=…&service_ids=…` ([masters.py](../backend/app/routers/masters.py), `get_slot`). Слоты не хранятся в базе, а считаются на каждый запрос:

1. мастер активен, все услуги активны и мастер их делает — иначе 404 / 422;
2. длительность = сумма длительностей выбранных услуг;
3. берётся смена мастера на эту дату; нет смены — пустой список;
4. перебираются начала от начала смены с шагом 15 минут, пока `начало + длительность <= конец смены`;
5. выбрасываются начала, где интервал `[начало, начало + длительность)` пересекается с записью `pending` / `confirmed`, и начала в прошлом.

Ответ — список начал в виде `datetime` с часовым поясом.

### Создание записи и защита от двойной записи

`POST /api/appointments` повторяет те же проверки, что и расчёт слотов: клиенту нельзя доверять, он мог прислать любое время. Затем запись и её состав сохраняются одной транзакцией.

Два клиента могут нажать «Записаться» на одно время одновременно: оба пройдут проверку пересечения запросом, пока ни одна запись ещё не сохранена. Тогда второй `INSERT` отклонит сама база ограничением `ex_appointments_no_overlap` (SQLSTATE `23P01`). SQLAlchemy превращает это в `IntegrityError`, эндпоинт делает `rollback` и отвечает `409 Время уже занято` — тем же ответом, что и обычная проверка.

### Статусы

```
pending ──→ confirmed ──→ completed
   │            │    └──→ no_show
   └────────────┴──→ cancelled   (POST /cancel)
```

Подробно — диаграмма состояний в [readme](../readme.md#диаграммы).


## 7. Ошибки

FastAPI отвечает JSON вида `{"detail": "текст"}`; ошибки валидации Pydantic — `{"detail": [{"loc": …, "msg": …}, …]}`.

| Код | Когда |
|---|---|
| 401 | нет токена, токен просрочен, отозван выходом или неверный email / пароль |
| 403 | роль не подходит (клиент открыл админский раздел, мастер пытается отменить запись или записаться) |
| 404 | объекта нет, или это чужая запись |
| 409 | конфликт с существующими данными: время занято, email или название уже есть, второй отзыв, повторная отмена, у смены есть записи, в категории есть услуги |
| 422 | данные не подходят по правилам: неверный формат, время вне смены или в прошлом, отмена позже чем за 2 часа, недопустимый переход статуса, отзыв до визита |

## 10. Запуск без Docker

Для разработки бэкенда отдельно от остального:

```
cd backend
python -m venv .venv
.venv\Scripts\activate          (Windows; в Linux/macOS — source .venv/bin/activate)
pip install -r requirements.txt
copy .env.example .env          и вписать свой DATABASE_URL
alembic upgrade head
python -m app.seed
uvicorn app.main:app --reload
```

API — `http://127.0.0.1:8000/api`, Swagger — `http://127.0.0.1:8000/docs`. Фронтенд в режиме разработки (`npm run dev`) сам проксирует `/api` на этот адрес.
