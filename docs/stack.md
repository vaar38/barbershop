# Обоснование стека технологий

Выбор шёл от трёх требований задачи:

1. **Нельзя допустить двойную запись** к мастеру, даже если два клиента нажимают кнопку одновременно.
2. **Время считается в минутах**, с учётом смен и одного часового пояса, а цена — в деньгах без ошибок округления.
3. **Три роли** с разными правами и SPA-интерфейс, которым удобно пользоваться с телефона.

Плюс условия учебного проекта: небольшая команда, ограниченное время, проект должен запускаться у преподавателя одной командой.

```
React SPA  ──HTTP/JSON──▶  Nginx  ──▶  FastAPI  ──SQLAlchemy──▶  PostgreSQL
                             │
                             └── отдаёт собранный фронтенд
```


## Архитектура: монолит + SPA

Один бэкенд-сервис и одно одностраничное приложение.

| Вариант | Почему нет |
|---|---|
| микросервисы | для 11 таблиц и одной команды это лишние сети, деплой и согласование данных между сервисами; выгоды нет |
| серверный рендеринг (Django-шаблоны) | у сервиса много интерактива: выбор услуг, мастера, слота без перезагрузки страницы; в SPA это проще и отзывчивее |

API и фронтенд разделены контрактом (раздел «API» в readme), поэтому их можно разрабатывать параллельно.


## Бэкенд

### Python + FastAPI

- **Документация API строится сама.** Swagger на `/docs` генерируется из кода, по нему фронтенд и тестировщик проверяют контракт без отдельного документа.
- **Валидация через Pydantic.** Схема запроса описывается один раз, неверные данные отсекаются до бизнес-логики с понятной ошибкой 422.
- **Зависимости (`Depends`).** Сессия базы, текущий пользователь и проверка роли подключаются к эндпоинту одной строкой — права не размазаны по коду.
- **Python команда уже знает** (предыдущий проект — сервис аренды автомобилей на том же стеке), значит меньше времени на освоение и больше на предметную логику.

| Альтернатива | Почему не выбрали |
|---|---|
| Django + DRF | много готового (админка, ORM), но тяжелее, свой ORM слабее для нестандартных ограничений PostgreSQL, сериализаторы многословнее схем Pydantic |
| Flask | валидацию, документацию и DI пришлось бы собирать из отдельных библиотек |
| Node.js (Express / NestJS) | второй язык в проекте без явной выгоды; опыт команды — в Python |

### SQLAlchemy 2 + Alembic

- **SQLAlchemy** — самая зрелая ORM в Python: модели в коде, транзакции, а при необходимости — любые конструкции PostgreSQL.
- **Alembic** хранит историю схемы в миграциях: база у всех разработчиков и в Docker создаётся одинаково командой `alembic upgrade head`. Миграции генерируются из моделей, а то, что ORM не описывает (расширение `btree_gist`, ограничение `EXCLUDE`), дописывается вручную.

Альтернатива — писать SQL руками: больше кода, нет миграций, ошибки в запросах видны только при выполнении.

### Pydantic v2

Описывает, что API принимает и отдаёт. За счёт `response_model` в ответ никогда не попадут лишние поля (например, `password_hash`). Типы `EmailStr`, `Literal`, `Field(ge=1, le=5)` заменяют ручные проверки.

### JWT (PyJWT) + bcrypt (pwdlib)

- **JWT** подходит для SPA: токен хранится на клиенте и передаётся в заголовке, серверу не нужно хранить сессии. Короткий access (30 мин) + refresh (7 дней) — компромисс между безопасностью и удобством.
- **Выход** реализован через `token_version` в таблице пользователей: увеличили номер — все старые токены недействительны. Не нужен чёрный список токенов.
- **bcrypt** — медленный по замыслу хеш для паролей. `pwdlib` выбран вместо `passlib`, который больше не развивается.

| Альтернатива | Почему не выбрали |
|---|---|
| сессии в cookie | нужно хранилище сессий и защита от CSRF; для API + SPA JWT проще |
| OAuth / внешний провайдер | избыточно для учебного проекта, лишняя внешняя зависимость |


## База данных: PostgreSQL

Главная причина — **ограничение исключения (`EXCLUDE`)**:

```sql
EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&)
WHERE (status IN ('pending', 'confirmed'))
```

Оно гарантирует на уровне базы, что у одного мастера не будет двух активных записей на пересекающееся время — даже при одновременных запросах. Проверка в коде без этого ненадёжна: два запроса могут одновременно убедиться, что время свободно, и оба записать.

Также нужны:

- `timestamptz` и тип диапазона `tstzrange` — для записей с часовым поясом и полуоткрытых интервалов `[начало, конец)`;
- `numeric(10,2)` — точные деньги без ошибок `float`;
- `CHECK`-ограничения — правила данных (уровень мастера, статус, оценка 1–5), которые нельзя обойти;
- транзакции — запись и её состав сохраняются вместе.

| Альтернатива | Почему не выбрали |
|---|---|
| MySQL / MariaDB | нет ограничений исключения и типов диапазонов; защиту от пересечений пришлось бы делать блокировками или триггерами |
| SQLite | нет `EXCLUDE`, слабая конкурентная запись, неудобно в многоконтейнерном окружении |
| MongoDB | данные явно реляционные (запись ↔ мастер ↔ услуги ↔ смены), нужны внешние ключи и транзакции |

Подробнее сравнение способов защиты от двойной записи — в [Анализ.md](../Анализ.md), раздел 3.2.


## Фронтенд

### React + TypeScript + Vite

- **React** — самая распространённая библиотека интерфейсов: много материалов и готовых решений, компонентный подход хорошо ложится на шаги записи (филиал → услуги → мастер → время).
- **TypeScript** ловит ошибки до запуска: типы ответов API описаны в одном месте (`src/api/index.ts`), и при изменении поля компилятор покажет все места, где оно используется.
- **Vite** — быстрый сервер разработки и сборка; Create React App устарел и больше не поддерживается.

| Альтернатива | Почему не выбрали |
|---|---|
| Vue | сопоставим по возможностям; React выбран из-за опыта и экосистемы |
| Angular | тяжеловесен для приложения из десятка экранов |
| чистый JS без фреймворка | ручное управление состоянием шагов записи и кабинетов быстро становится запутанным |

### React Router

Отдельные адреса для страниц (`/masters/3`, `/book?master_id=3`) — ссылкой на мастера можно поделиться, кнопка «назад» работает. Nginx отдаёт `index.html` на любой путь, дальше маршрут разбирает React Router.

### TanStack Query

Загрузка данных с сервера: кеш, состояния «загрузка / ошибка», повтор запроса. Главное — **инвалидация**: после записи или отмены достаточно сбросить ключи `appointments` и `slots`, и все экраны, где они показаны, обновятся сами. Без библиотеки это пришлось бы делать вручную на каждой странице.

Альтернатива — Redux: для данных с сервера в нём больше шаблонного кода, а кеширование всё равно пишется отдельно.

### CSS Modules

Стили лежат рядом с компонентом, имена классов не пересекаются между страницами. Не нужна отдельная библиотека компонентов — интерфейс небольшой, а свой стиль (прайс-лист, шаги записи) проще сделать самим.


## Инфраструктура

### Docker Compose

Весь проект — база, бэкенд, фронтенд и Nginx — поднимается одной командой `docker compose up -d --build` на любой машине с Docker. Версии PostgreSQL, Python и Node зафиксированы в образах, поэтому «у меня работает, у вас нет» не возникает. Миграции применяются автоматически при старте бэкенда.

### Nginx

- отдаёт собранный фронтенд (статические файлы);
- проксирует `/api` на бэкенд — **фронт и API на одном адресе**, поэтому не нужна настройка CORS;
- на неизвестные пути отдаёт `index.html`, чтобы работали адреса страниц SPA.

Фронтенд собирается внутри Docker в два этапа: Node собирает статику, в итоговый образ попадает только Nginx с готовыми файлами — образ маленький, Node в нём нет.

### GitHub Actions

На каждый push запускаются линтер, проверка форматирования, тесты и сборка фронтенда. Ошибка видна в pull request до слияния в `main`.


## Качество кода

| Инструмент | Зачем |
|---|---|
| pytest + httpx | тесты API бэкенда |
| Vitest + Testing Library | тесты фронтенда: функции форматирования, клиент API, доступ по ролям, сценарий записи; Vitest использует ту же конфигурацию, что и Vite |
| ESLint | ошибки в коде фронтенда и правила хуков React |
| Prettier | единое форматирование, без споров о стиле в ревью |
| flake8 | стиль и ошибки в Python-коде |


## Итог

| Требование | Чем закрыто |
|---|---|
| нет двойной записи | `EXCLUDE` в PostgreSQL + проверка в FastAPI + ответ 409 |
| время в минутах, часовой пояс, точные цены | `timestamptz`, `tstzrange`, `numeric`, `Decimal` в Python |
| три роли с разными правами | JWT + зависимости FastAPI на сервере, `RequireRole` на клиенте |
| удобный интерфейс записи | React SPA, TanStack Query, адаптивная вёрстка |
| запуск одной командой | Docker Compose + Nginx |
| понятный контракт API | Swagger, сгенерированный FastAPI из схем Pydantic |
